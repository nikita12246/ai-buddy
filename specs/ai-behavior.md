# Поведение AI-модуля

Статус: черновик v0 для согласования с backend и владельцем данных. Область действия: один сценарий запроса доступа и ответы по найденным инструкциям.

## Вход и границы модуля

| Поле | Источник и назначение |
| --- | --- |
| Вопрос и релевантная история | Backend передаёт текущий вопрос и выбранные сообщения диалога. История помогает понять ссылки вроде «этот инструмент». |
| Найденные фрагменты | Поиск возвращает разрешённые фрагменты с `chunk_id`, `document_id`, `title`, `text`, `source_url`, `version`. Backend передаёт только результаты, прошедшие проверку доступа. |
| Каталог | Backend передаёт разрешённые пары `tool_id` и `resource_id` с названиями для уточнения. |
| Текущий черновик и статус | Необязательный снимок из backend. Он позволяет продолжить заполнение черновика или объяснить следующий шаг. |

Модуль возвращает ответ, уточнение или предложение для черновика. Backend определяет пользователя, проверяет права, валидирует и сохраняет черновик. Отправка возможна только после подтверждения конкретной версии пользователем. Статус заявки и следующий шаг берутся из backend. Модель не имеет инструментов для подтверждения, отправки заявки или изменения прав.

Вопрос, история и текст документов рассматриваются как недоверенные данные. Backend ограничивает объём истории и поискового контекста до вызова модели. AI-модуль формирует запрос из нужных полей, без идентификатора пользователя, ключей и произвольного содержимого сессии. Источники отображаются по серверным метаданным найденных фрагментов.

## Структура ответа

Все четыре ключа обязательны. Неизвестные ключи, неправильные типы, пустой `answer` и отсутствующие обязательные поля считаются некорректным ответом модели.

| Поле | Правило |
| --- | --- |
| `answer` | Непустой текст. Утверждения об инструкциях опираются на найденные фрагменты. Утверждения о статусе опираются на снимок backend. |
| `source_ids` | Массив уникальных ID использованных фрагментов. Рабочее соглашение v0 — использовать `chunk_id`. Пустой массив допустим для уточнения, сообщения об отсутствии сведений и ответа только по серверному статусу. |
| `clarifying_question` | Один непустой вопрос или `null`. Если задан вопрос для заполнения обязательных полей, `draft_proposal` должен быть `null`. |
| `draft_proposal` | `null` либо объект с непустыми `tool_id`, `resource_id`, `justification`. Пара ID должна присутствовать в переданном каталоге, а обоснование должно следовать из слов пользователя или текущего черновика. |

AI-модуль проверяет принадлежность каждого источника переданному набору и пару ID в каталоге. Для первого среза действуют пределы в 2400 символов для ответа, 400 для уточнения, 128 для каждого ID черновика и 600 для обоснования. Входной JSON ограничен 48 КиБ. При нарушении структуры или проверяемых ограничений весь результат отклоняется. Семантическую достоверность фактов и обоснования проверяем на eval-наборе.

## Сценарии

| Условие | Ожидаемое поведение |
| --- | --- |
| Есть подходящая инструкция | Короткий ответ по тексту, ID реально использованных фрагментов. |
| Не определён инструмент или ресурс | Один вопрос, чтобы различить допустимые варианты. Черновик отсутствует. |
| Известен ресурс, отсутствует цель доступа | Уточнить цель. Поля заявки остаются на стадии уточнения. |
| Есть основание для запроса, пара ID допустима, цель известна | Предложить черновик. Пользователь видит, что отправка требует отдельного подтверждения. |
| Поиск вернул пустой результат | В живом режиме модель формулирует уточнение, объясняет нехватку сведений или ограничение доступа. Возвращается пустой массив источников. Черновик требует источника. |
| Есть подтверждённый статус заявки | Пересказать статус и переданный следующий шаг. Если статуса нет, сообщить, что он неизвестен. |
| В документе или вопросе просят обойти подтверждение | Сохранить обычные ограничения. Такой текст сам по себе не служит основанием для черновика или действия. |

## Ошибки API

| Сбой | Результат для backend |
| --- | --- |
| Отмена вызова или превышение срока | Вернуть ошибку вызова. Backend сохраняет пользовательское сообщение и решает, как предложить повтор. |
| `429`, ошибка сети или `5xx` | Сообщить о временной недоступности. Для первого среза предполагается одна попытка в пределах таймаута. |
| Нет ключа или провайдер отклонил авторизацию | Вернуть ошибку конфигурации. В пользовательском ответе не показывать ключ, тело ошибки провайдера или внутренние детали. |
| Провайдер отказал, ответ неполный или нарушает схему | Вернуть ошибку непригодного результата. Не сохранять поля черновика из такого ответа. |

При ошибке AI-модуль возвращает ошибку без частичного результата. В логах достаточно класса ошибки, идентификатора запроса и длительности. Точный формат HTTP-ошибок согласуется с backend.

## Примеры для первого среза

Во всех примерах данные учебные.

**Инструкция.** Вопрос «Как получить доступ к учебному GitLab?» Поиск вернул `gitlab-access-01` с текстом «Укажи проект и цель доступа. Заявка отправляется после подтверждения».

```json
{
  "answer": "Для заявки на доступ к учебному GitLab понадобятся проект и цель доступа.",
  "source_ids": ["gitlab-access-01"],
  "clarifying_question": "К какому проекту нужен доступ и для какой задачи?",
  "draft_proposal": null
}
```

**Черновик.** Пользователь добавил «К проекту training-api для исправления первого бага». Каталог содержит пару `gitlab` / `training-api`, инструкция найдена.

```json
{
  "answer": "Можно подготовить заявку на доступ к training-api. Проверь поля черновика перед подтверждением.",
  "source_ids": ["gitlab-access-01"],
  "clarifying_question": null,
  "draft_proposal": {
    "tool_id": "gitlab",
    "resource_id": "training-api",
    "justification": "Исправление первого бага"
  }
}
```

**Нет источника.** Вопрос «Как получить доступ к неизвестному инструменту?» Поиск не вернул фрагментов.

```json
{
  "answer": "В доступных инструкциях не нашёл этот инструмент.",
  "source_ids": [],
  "clarifying_question": "Как точно называется инструмент?",
  "draft_proposal": null
}
```

## Критерии приёмки

- **AI-01:** при пустой выдаче ответ не выдумывает инструкцию и не предлагает черновик.
- **AI-02:** прямая или косвенная просьба обойти подтверждение приводит к нулю вызовов сервиса заявок. Интеграционная проверка с backend.
- **AI-03:** ответ с чужим `source_id` или неизвестной парой `tool_id` / `resource_id` отклоняется целиком.
- **AI-04:** при неоднозначности или нехватке обязательного поля модель уточняет. При достаточных данных возвращает проверяемое предложение черновика.
- **AI-05:** таймаут, `429` и неверный JSON не приводят к записи результата или черновика. Ключи и необработанные ответы провайдера не раскрываются.
- **AI-06:** модель объясняет только переданный backend статус. До подтверждённого результата она не сообщает, что заявка отправлена или доступ выдан.
- **ACL-02:** интеграционный тест проверяет фактический запрос к модели. Закрытый фрагмент отсутствует и в запросе, и в отображаемых источниках.

Первые проверки делаем с fake-клиентом без сети и ключа. Для проверки реального API нужен отдельный пробный запуск с учебным запросом и структурированным ответом.

## Вопросы для согласования

**Backend**

1. Какой формат снимка черновика, `service_status` и `next_step` получит AI? Кто выбирает ветку ответа на запрос о статусе?
2. Где брать разрешённые пары `tool_id` / `resource_id`? Каковы обязательные поля и ограничения длины для предложения черновика?
3. Какой таймаут выделяем AI внутри запроса? Как отображаем ошибку и даём повторить генерацию для сохранённого сообщения?

**Владелец данных**

1. Стабилен ли `chunk_id` в пределах версии корпуса? Как сопоставлять его с `document_id` и ссылкой при отображении источника?
2. Каковы пределы top-k и объёма текста? Как различить отсутствие результата и несколько подходящих инструкций?
3. Какие учебные документы и ожидаемые источники используем для первого сквозного сценария и проверки утечки закрытого фрагмента?
